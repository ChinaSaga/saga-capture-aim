# 架构与源码索引

面向「要改代码」的人。全部源码在 `src\`，分三层：

```
应用层（原易语言主程序的 C++ 翻写）     引擎层（原 Saga.dll，现已编进 EXE）     第三方（vendored）
  main.cpp   启动 / 线程装配              OpnecvCapture.cpp  DirectShow 采集      Makcu\  串口 + Cat + asio
  Ui.cpp     Win32 界面 / 画板             NCNN.cpp           NCNN(Vulkan) 推理     ONNX 侧 *.hpp
  Util.cpp   工具 / 配置底座 / PID         ONNX.cpp           ONNX(DirectML)
  Capture.cpp 开始采集 / 双机UDP / 截图    Mouse.cpp          模拟轨迹网络
  Aim.cpp    推理循环 / 选靶 / 移动        Makcu\*            串口鼠标
```

> 历史背景：原来是 `Saga.dll` + `SagaApp.exe` 两个工程，2026-09-27 合并成一个 Application。
> 所以看到 `saga::` 命名空间＝原 DLL 的引擎函数，`sagaXxx()`（如 `sagaSetCapture`）是应用层薄封装。

## 2. 数据流

```
采集卡 DirectShow 回调
  FrameReceiver::BufferCB
    ├─ 持 producerLock_（SRW 独占）：中心裁剪 + YUV→BGR，写进某个空闲槽的像素区
    ├─ 极短持 g_snapshotLock：发布 g_captureFrame（shared_ptr）并 ++g_captureSequence
    └─ WakeAllConditionVariable(&g_frameReady)
                    ↓
推理线程 aimThread(1|2)
  captureAcquire(frame, seq, 50ms)            ← 超时只是用来复查运行状态，不是每帧等待
  ncnnDetectBgr / onnxDetectBgr(frame.bmp+54, w, h, stride, conf, nms, objs)
  frame = {}                                  ← 立刻归还槽位（硬性约定）
                    ↓
  objs(≤99) → 构建 targets[] → aimlock::select 选靶 → nomRatioRel 算偏移 → moveDx/moveDy
                    ↓
  threadMove=true ? mouseMoveThread 消费      : 立刻 aimMoveOnce()
                    ↓
  trajMove10/5/3（分段 hiSleep 0.885ms）或 makcuMove → SerialPort → 硬件
```

双机模式（本机不接卡）：外部采集机把 **JPEG / BMP** 以 1472 字节分包 UDP 发到 `:6666`
→ `frameThreadUdp` 累积到非满包为止 → `g_frame.swap()` 发布 → `++g_frameSeq` → 唤醒 `g_publishedFrameReady`。
> 本仓库**没有发送端**；UDP 线程只在 `startCapture` 没成功（即 `g.noConvert == false`）时才启动。

## 3. 帧格式与帧池（改这里前先看）

- 每块内存 `_aligned_malloc(size+64, 64)`，`buffers_[i] = storage_[i] + 10`（故意偏移，使像素起点 64 字节对齐）。
- `size = 54 + stride*crop`，`stride = (crop*3 + 3) & ~3`（4 字节对齐）。
- 前 54 字节是一次性写好的 BMP 头：`BITMAPFILEHEADER` + `BITMAPINFOHEADER`，其中 **`biHeight = -crop`（top-down 正序）**、
  `biBitCount = 24`、压缩 `BI_RGB`。像素从 `bmp + 54` 开始，BGR24。
- **8 槽是「最新帧池」不是队列**：只有 `use_count() == 1`（无人引用）的槽才能写；8 槽全被租借时回调直接丢帧。
  消费者拿到的 `shared_ptr` 会让这块内存保活，重建采集后旧引用依然有效。
- 所有权：`CaptureFrame{owner, bmp, size, width, height, stride}`；`frame = {}` 即归还。
  **做磁盘 I/O 前必须先归还**（`frameThreadShotSave` 里显式这么写）。
- NCNN/ONNX 有「BMP 零拷贝快速路径」：头必须是 `BM`、`offBits≥54`、top-down、24 位、`stride == (w*3+3)&~3`，
  任一不满足就退回 `cv::imdecode`（性能骤降）。

**锁顺序唯一：`producerLock_ → g_snapshotLock`**；`captureAcquire` 只拿 `g_snapshotLock`，不存在逆序。

## 5. 编码体系<a name="编码体系"></a>

- **内部一律 GBK(CP936)**：字符串比较、Win32 A 系列 API、中文路径。
- **对外 UTF-8**：`圣人自用.js`（UTF-8 + CRLF）、HTTP JSON、网页。
  - 读 → `utf8ToAnsi`；写 → `ansiToUtf8` 且 LF→CRLF（这样回写的文件与易语言原版逐字节一致）。
- **引擎枚举返回的设备名是运行时 UTF-8**（内部走 `WideCharToMultiByte(CP_UTF8)`，与编译期字符集无关）：
  显示前 `utf8ToAnsi`，**回传给 `setcjk_ex` 前必须 `ansiToUtf8`**。
- `"成功"` 判定：引擎源码已与本 EXE 同字符集编译，`Capture.cpp` 里直接比字面量即可（DLL 时代才需要转码）。
- UI 里的 DXGI 显卡描述另用 `ansiFromWide()`。

## 7. 改代码前必须知道的坑

1. **持锁不做重活**：`BufferCB` 在整个裁剪+像素转换期间持 `producerLock_`；任何长时间不归还帧的逻辑会让 8 槽占满 → 静默丢帧。
2. **`aimThread` 内的数组必须是局部变量**（源码注释也这么写）：两个推理线程各一份，
   写成 `static` 会串状态。`Memory lockMem` 同理。
3. **NCNN 的全局静态不是线程安全的**：假定单推理线程；`aimThread(1)` 和 `(2)` 各用 NCNN / ONNX，互不重叠。
4. **切换识别范围必须走 `applyCropSize()`**：暂停推理 → 用记住的参数重建采集 → 等 2000ms 新画面 → 恢复。
5. **`g_captureSequence` 跨重启不重置**：消费者自己的 `sequence` 初始为 0 且**不要重置**（重置会拿到旧帧）。
6. **NCNN 的 `imgWH` 从 `.param` 里解析**（`pnnx_189` / `pnnx_fold_anchor_points`），非 pnnx 导出模型会退回 **416**。
7. **像素只读**：给 OpenCV 的 `Mat` 是只读包装，禁止写入。
8. **UDP 的帧边界靠包长判断**：最后一包恰好 1472 字节会粘包；没有重排、没有校验。
9. **UDP 会反向改写 `g.imgSize`**（每 100 帧从收到的图取宽），与本地裁剪设置可能打架。
10. **热键 key=4 没有映射**：`MapMouseButton` 只认 1/2/3/5/6，所以网页「热键4」恒为假。
